  <behavior>
    - cas_counterexample: initial k = x; entry 1 is CAS(k, expected y, desired z) which fails; entry 2 is CAS(k, expected x, desired y) which succeeds. A fuzzy snapshot with start index 0 that observes k = y (stamp 2), restored and replayed from index 1, ends with k = y.
    - tombstone_newer_than_snapshot_is_kept: k = x; entry 1 CAS(k, absent, q) fails; entry 2 CAS(k, x, delete) succeeds. Start index 0, snapshot observes the tombstone with stamp 2 which scan must yield; replay ends with k absent.
    - tombstone_at_or_below_start_is_dropped: a tombstone with stamp at or below the start index is absent from the scan and replay still matches sequential apply.
    - naive_replay_diverges_on_counterexample: restoring the cas_counterexample snapshot with every stamp forced to 0 ends with k = z, proving the test discriminates.
    - fuzzy_replay_model (proptest): random single-key SET/DEL/CAS histories over 4 keys and 3 values, random start index a, random number of extra entries applied between scanned keys; restored-then-replayed engine equals the sequentially applied engine on every key.
  </behavior>
  <action>
Add the tests above to `mod tests` in src/raft/state_machine.rs, built on a test-only helper `fuzzy_snapshot_replay(history: &[Op], a: usize, extra_per_key: &[u8]) -> LocalEngine` where Op is a test-local enum (Set, Delete, Cas over small integer keys and values rendered to bytes). The helper does exactly this: apply history[0..a] to a live engine with stamps 1..=a; apply extra_per_key[0] further entries (clamped to the history length); call live.scan_versioned(a as u64, ...) and inside the callback record the VersionedEntry then apply the next extra_per_key[i] entries to the same live engine (this models writes racing with the scan: later keys are observed after newer writes); load every recorded entry into a fresh engine with load_record; replay history[a..] with stamps a+1.. via the engine's *_at methods; return the restored engine. The property compares `get` of every key against a second engine that applied the whole history sequentially. Use proptest with ProptestConfig::with_cases(3000), history length 1..60, and a strategy that biases CAS expected values toward values that are likely to match (so successful and failed CAS both occur). Note the constraint in a test-module comment: only single-key operations are covered; multi-key conditionals (FR-2 WATCH) would need a consistent-cut snapshot and must reopen this design (assumption A12, deferred).
