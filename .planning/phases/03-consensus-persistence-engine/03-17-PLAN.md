  <action>
Client full_snapshot: open or reuse the snapshot-lane connection (a PeerClient built by new_snapshot_client already dials Lane::Snapshot); send SNAP_BEGIN { vote, meta, total_len = snapshot.snapshot.len }; read the file with positional reads inside tokio::task::spawn_blocking in chunks of option.snapshot_chunk_size().unwrap_or(cfg.snapshot_chunk_size) (a bulk, off-hot-path read, so blocking reads are appropriate here) and send each as SNAP_CHUNK with the offset in a fixed 8-byte big-endian body prefix and the bytes as the body tail (not re-encoded); allow at most cfg.snapshot_ack_window chunks outstanding and wait for a SNAP_ACK carrying the written byte count before sending more (backpressure); finish with SNAP_END and return the SNAP_RESP SnapshotResponse. Server snapshot-lane state machine per connection (replaces the unknown-kind close from 03-09): SNAP_BEGIN creates recv_dir/recv-<n>.tmp with create_new and mode 0600 where n comes from a server-wide AtomicU64 (no peer-supplied path component ever) and records total_len and written = 0; each SNAP_CHUNK must have offset equal to bytes written, otherwise delete the tmp file, send KIND_ERROR and close; the chunk bytes are appended with a positional write, written advances, ServerStats.snapshot_chunks increments, and a SNAP_ACK { written } is sent every snapshot_ack_window chunks; SNAP_END requires written == total_len, syncs the file, then calls handler.install_snapshot(vote, meta, SnapshotFile { path, len }) and sends SNAP_RESP with the handler's result (a handler error is sent as KIND_ERROR). The guardrails (size bounds, cleanup on every exit path, idle timeouts, cancel, ack-window enforcement, one receive per connection) are completed and tested in Task 2.

Tests in tests/transport.rs (extend StubHandler with an install_snapshot recorder): snapshot_transfer_chunked_and_installed: a 3 MiB file of non-repeating bytes sent with option chunk size 256 KiB arrives byte-identical at the path handed to install_snapshot, ServerStats.snapshot_chunks equals the expected 12, the response reaches the client, and inside the stub's install_snapshot the received file name matches recv-<digits>.tmp, lives directly in recv_dir and has mode 0600 on unix (recv_dir contains no other file).

<task type="auto" tdd="true">
  <name>Task 2: Snapshot guardrails - offset and size validation, cleanup on every exit path, idle timeouts, cancel and ack-window backpressure</name>
  <files>src/net/client.rs, src/net/server.rs, tests/transport.rs</files>
  <read_first>src/net/client.rs and server.rs (Task 1); 03-RESEARCH.md Pitfall 8 and the Security Domain rows for snapshot chunk flood and path traversal; openraft src/network/v2/network.rs full_snapshot (cancel future, StreamingError variants)</read_first>
  <behavior>
    - snapshot_bad_offset_rejected: a raw peer sends SNAP_BEGIN then a SNAP_CHUNK whose offset differs from bytes written; the server deletes its tmp file, sends KIND_ERROR, closes, and the stub's install_snapshot is never called
    - snapshot_over_declared_size_rejected: chunks whose offset plus length exceeds the declared total_len are rejected the same way; SNAP_END with written different from total_len is rejected and the tmp file removed
    - snapshot_begin_over_max_rejected: total_len above max_snapshot_bytes is refused at SNAP_BEGIN and no tmp file is created
    - snapshot_second_begin_rejected: a second SNAP_BEGIN on a connection with an active receive closes the connection and removes the tmp file (one active receive per connection)
    - snapshot_early_close_removes_tmp: the sender drops the TCP connection mid-transfer and the receiver leaves no file in recv_dir
    - snapshot_cancel_aborts_and_removes_tmp: resolving the cancel future stops the client send promptly with the cancellation error and the receiver cleans up
    - snapshot_idle_timeout_cleans_up: a sender that stalls longer than snapshot_idle_timeout (200 ms in the test) leaves no tmp file and the server connection is closed; a receiver that stops acking makes the client fail with Timeout after the same idle bound (the bound is per chunk, not total)
    - snapshot_ack_window_bounds_outstanding_chunks: with snapshot_ack_window = 2 and a stub receiver that delays acks, the sender never has more than 2 chunks unacknowledged (observed through a counter in the test server)
  </behavior>
  <action>
Implement the guardrails behind the behavior list. Server: SNAP_BEGIN rejects total_len above cfg.max_snapshot_bytes before creating any file; the receive state (tmp path, written, total_len) lives in a guard value whose Drop deletes the tmp file unless install hand-off completed, so every exit path (error, close, idle timeout, task abort) removes it; each SNAP_CHUNK must also satisfy offset plus length not above total_len; enforce one active receive per connection; apply cfg.snapshot_idle_timeout to every read between frames on the snapshot lane (a stalled sender is closed and cleaned up). Client: wait for each required SNAP_ACK under cfg.snapshot_idle_timeout as a per-chunk idle timeout (Pitfall 8: openraft's install_snapshot_timeout is a 200 ms default total and must not be applied as a total to a multi-GB transfer; plan 03-13 raises it, this idle timeout is the real bound); race the whole send against the cancel future and return the cancellation StreamingError; map socket errors to Unreachable, timeouts to Timeout and protocol violations to Network; always drop the snapshot connection after a failure so the next call reconnects. Add the behavior-list tests to tests/transport.rs; the hostile-peer tests use a raw TcpStream with a hand-written Hello and frames built with the shared FrameCodec so they can send illegal sequences the real client never would.
