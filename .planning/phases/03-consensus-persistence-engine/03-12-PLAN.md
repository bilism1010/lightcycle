<objective>
Milestone 3.4 integration (decisions D-09, D-10): connect the stamped state machine core (plan 03-05) to the snapshot store (plan 03-10) through openraft's RaftStateMachine trait.

Purpose: this is where openraft's snapshot lifecycle meets the fuzzy snapshot design: the builder captures the applied index at creation, the scan runs off the runtime, durability precedes return (so the subsequent log purge is safe), and install replaces the whole engine atomically with readers keeping their old Arc. The trigger itself (every N applied entries, default 1,000,000) is openraft's SnapshotPolicy::LogsSinceLast configured in plan 03-13; this plan enforces "no overlapping builds" (Pitfall 11) and keeps exactly one snapshot.

Output: the RaftStateMachine implementation and tests in src/raft/state_machine.rs.
</objective>

Implement `impl RaftStateMachine<TypeConfig> for KvStateMachine` with SnapshotData = SnapshotFile and SnapshotBuilder = KvSnapshotBuilder. applied_state returns (last_applied, last_membership). apply consumes the stream: for each Ok((entry, responder)) call apply_entry, send the KvResponse through the responder when present, and every 256 entries await tokio::task::yield_now() so a maximum 4096-entry batch cannot monopolize the runtime thread (assumption A8; no epoch guard exists in this scope). try_create_snapshot_builder(force) first tries to take the build lock with try_lock_owned and returns None if it is held; otherwise it captures, in this call (serialized with apply because the method takes &mut self and openraft's worker invokes it between apply commands), the Arc<LocalEngine>, meta.last_log_id = last_applied and meta.last_membership = last_membership, and returns a KvSnapshotBuilder holding the owned lock guard. get_snapshot_builder returns a builder that acquires the same lock inside build_snapshot (so builds are serialized, never concurrent).
